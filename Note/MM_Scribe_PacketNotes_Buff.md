## 1. 樣本與工具

| 檔案 | 內容（錄製者自述） |
|---|---|
| `base.pcapng` | 靜止對照組，無任何 buff 動作 |
| `add.pcapng` | 獲得一個**持續時間無限**的 BUFF |
| `expire.pcapng` | 8 秒單層 BUFF ×1、8 秒疊層 BUFF ×1（含戰鬥） |
| `stack.pcapng` | 無限可疊 2 層的 BUFF，疊到第 3 層轉成 5 秒單層 |

分析腳本：`Note/Ref/Buff pcapng/scan_buff.py`（`python scan_buff.py <目錄>`）。

**掃法：直接掃 magic，不走整條訊息鏈。** 初版試過「從對齊點一路 `off += 9 + clen`
串下去」，實測會漏掉大半事件——串流裡只要有一處對錯位撞出超大的 `contentLength`，
鏈就一口氣跳過幾十 KB 的真實訊息，而且「覆蓋率」看起來還是 99%（跳過的位元組
也被算成解析過了）。改成三重守門的 magic 掃描後，四份樣本共 76 筆事件，
與主程式探針逐封包掃出來的結果完全一致。

該腳本另有做 TCP 重組（主程式沒有）。重組時**同一個 seq 要取最長的那一筆**：
這條連線上有大量 6-byte 探測封包沿用前一個 seq，用 `setdefault` 會把真資料
換成那 6 bytes，實測吃掉四分之一的位元組、`stack.pcapng` 只剩 4/29 筆事件。

遊戲連線：`43.213.236.172:16000` ↔ 本機（單一長連線，四份錄影都在同一條上）。

## 2. Buff opcode（台版 2026-09 實測值）

| packetType | 十進位 | 長度 | 語意 | 對應 CHANNEL |
|---|---|---|---|---|
| `0x1ADE8` | 110056 | 36 | **Buff 新增** | `0x5045` (20549) |
| `0x1ADEA` | 110058 | 36 | **Buff 更新**（同 key、同 buffId、同時長，只有 `c` 欄變） | `0x5048` (20552) |
| `0x1ADE9` | 110057 | 16 | **Buff 移除／到期** | `0x5047` (20551) |

- 三者在 `base.pcapng` 出現次數皆為 **0**，其餘三份都有 → 差分成立。
- 每個 REPL 事件都有一則同 `(owner, key)` 的 CHANNEL 事件相隨，**四份樣本合計 18/18、7/7、10/10 完全配對**。
- 對應 `packet-protocol.md` 的 `REPLICATION_ActorBuff_Add/Refresh/Expire_REPL`。
  → **REPLICATION 族是獨立 packetType，不是共用通道包**，這點已由樣本確認。
- ⚠ 這是「今天台版的值」，與 `0x51E9`／`0x4FC5` 同樣會隨改版變動。

另有 `0x1B0CF` (110799, 24B) 與 `0x5046` (20550, 4B) 在部分 ADD 之後緊接出現，
內容為 `[8B buffKey][u32=6][u32][u32][u32]` 與 `[u32 buffId]`；用途未解。

## 3. ADD / UPD 內部佈局（content 相對 offset，36 bytes）

| offset | 長度 | 欄位 |
|---|---|---|
| 0..7 | 8 | **擁有者 entityId**（buff 掛在誰身上） |
| 8..15 | 8 | **buffKey**：這一次施加的**實例握把**。低位 byte 是同批次的序號（`00…` / `01…`），其餘隨時間遞增 |
| 16..19 | 4 | **buffId** (u32 LE)：buff **型別**鍵，跨場景、跨錄影穩定 |
| 20..23 | 4 | **持續時間** (float32 LE)，秒 |
| 24..27 | 4 | **層數**（u32）— 2026-09-06 實測確認，見 §4.2 |
| 28..35 | 8 | **來源 entityId**（誰施加的） |

REM（16 bytes）只有 `[8B 擁有者 entityId][8B buffKey]`。

### 持續時間欄位
- 有限時長是乾淨的 float32：`41000000`=8.0、`41200000`=10.0、`40A00000`=5.0、`41A00000`=20.0
- **無限持續不是固定哨兵，不能比對特定值。** 已觀測到兩個：

  | raw | float32 | 換算 |
  |---|---|---|
  | `0xD1B03913` | −94608973824.0 | −3000.0309 年 |
  | `0xD1B03914` | −94608982016.0 | −3000.0311 年 |

  差一個 ULP = **8192 秒 ≈ 2.28 小時**。這欄放的是一個「約 −3000 年」的絕對時間值，
  底層時鐘一直在走，但 float32 在這個量級只表示得出 8192 秒的間隔，
  所以要過約 2.3 小時才會跳到下一個可表示值 —— 同一段時間錄的樣本會全都一樣。

  ⚠ 初版就是被這點騙了：四份樣本全是 `...3913`，寫死成哨兵；隔幾天實機就撞到
  `...3914`，時長顯示成 `?D1B03914`。**判定改成範圍**：float32 解得出
  `0 < 秒數 < 1e7`（約 115 天）就是有限，否則（負值／0／NaN／超大值）一律當無限。
  真實 buff 的秒數與那個 9.46e10 差四個數量級，不會誤判。

### 4.2 層數欄位（offset 24）

**已確認是層數**：實機測試把一個可疊 buff 疊到 45 層，LOG 顯示 `層數=45`
（2026-09-06，錄製者實測回報）。

離線樣本中的序列也對得上錄製者對 `stack.pcapng` 的自述
（「無限可疊 2 層，疊到第 3 層轉成 5 秒單層」）：

```
ADD 0x2A3AF4EE INF 層數=1      ADD 0x284F3804 INF 層數=1
UPD 0x2A3AF4EE INF 層數=3      UPD 0x284F3804 INF 層數=2
ADD 0x7528A61D 5s  層數=1   ← 第三層轉成的 5 秒單層 buff
REM ×3
```

⚠ 讀 LOG 時的注意事項：層數不保證單調遞增，實測看得到 `1 → 3 → 2 → 1`
（掉層）與 `1 → 10 → 11`（一次跳多層）。這是遊戲機制，不是解析錯誤。

## 6. 主程式實作（開發者 LOG 探針）

已實作於 `_buff_scan` / `_buff_walk` / `_buff_report`（`BUFF_*` 常數區）。
**純觀測**：只在開發者模式跑、只寫診斷 LOG，不進任何統計，例外一律吞掉。

- **不維護串流狀態**。整則訊息只有 25／45 bytes，直接逐封包掃 magic 就好，
  不必像 `_mob_walk` 那樣接續跨封包的 body。被 TCP 切中的那幾則就是漏掉，
  與傷害事件同樣的已知代價（見 `PacketNotes_Damage.md` §2）。
- **三重守門**：opcode 相符 + `contentLength` 與該 opcode 的固定長度**完全**相等
  + `encodingType == 0`。實測 13MB 隨機資料誤命中 0 筆、`base.pcapng` 誤命中 0 筆。
- 三種 opcode 分開 `find()`，但**要照線序輸出**（`hits.sort` by offset）——
  同一個封包裡 ADD 與 UPD 的先後就是層數變化的順序，依 opcode 分組會把它洗掉。
- 去重鍵是 `(事件, 擁有者, key, c)`：ADD 會重送必須擋掉，但 `c` 的變化正是要觀測的
  目標，把它納入去重鍵才不會被吃掉。
- 這三個 opcode 的 content 都是 `enc == 0`（未壓縮），不需要 brotli。

實測（四份樣本逐封包餵 `_buff_scan`）：`base` 0 筆、`add` 18 筆、`expire` 29 筆、
`stack` 29 筆，與離線腳本重組後的結果完全一致。

## 7. 即時 Buff 監測面板

主畫面「技能傷害排行」之下，可折疊（`_build_buff_pane` / `toggle_buff_collapse`）。
列的樣式沿用技能排行的 `tk.Canvas` 進度條做法，只是填充色換綠（`BUFF_FILL_COLOR`）、
右側是剩餘秒數、點擊不展開。

- **只顯示 `owner == ident_self_entity` 的 buff**。還沒綁定角色 ID 時一列都不顯示。
- **`active_buffs` 的索引必須是 `(owner, buffKey)`**。buffKey 不是全域唯一的 ——
  實測 `007490FC1F2BEE07` 同時掛在三隻怪身上；只用 key 當索引會互相覆蓋，
  而且 REM 掉一隻就把另外兩隻的也刪了。
- **倒數靠本地時鐘**（`time.monotonic`），每 `BUFF_TICK_MS` 重繪一次。封包只在
  ADD/UPD 當下給一次總秒數，中間不會再送，所以 UPD 一律當作「重新開始倒數」。
- **倒數到 0 保持在 0，不清除**。到期是由 REM 封包宣告的；自行清掉會在漏包時
  讓畫面與遊戲不符。只有收到 REM 才刪。
- **無限持續的 buff** 顯示 `∞`、進度條固定滿格（沒有秒數可以倒數）。
- **層數接在名稱後面顯示 `×N`，1 層不標**——大部分 buff 一輩子都是 1 層，
  每列都掛個 `×1` 只是雜訊。
- `BUFF_ACTIVE_MAX` 上限：換場景時舊實體不會送 REM，沒有上限就是純漏水。
  自己的 buff 只有個位數，額度幾乎都花在場上其他實體身上。
- **偵測一律跑，「開始/停止」只管顯示**。`_buff_scan` 在 `packet_callback` 的
  `is_monitoring` 檢查**之前**，理由同身分偵測：ADD 一輩子只送一次，沒在收就
  永遠等不到。診斷 LOG 那份輸出另外看開發者模式。
- **面板三種狀態**（`update_buff_list` 開頭決定資料來源）：

  | 狀態 | 來源 | 時鐘 |
  |---|---|---|
  | 還沒按過開始 | 空 | — |
  | 監控中 | `active_buffs`（背景快取） | `time.monotonic()` |
  | 已按停止 | `_buff_frozen_view`（快照） | `_buff_frozen_at`（定值） |

- **`end` 存的是絕對 monotonic 時間**，所以按開始時剩餘秒數自然正確：
  10 秒前拿到的 30 秒 buff，按下去就顯示 20 秒。這是「背景暫存」能成立的關鍵，
  不要改成存「剩餘秒數」再自己扣。
- **停止時的快照要逐筆 `dict(v)` 複製**。快取在背景還會繼續更新層數／重設秒數，
  共用同一個 dict 的話凍結畫面會被偷偷改掉。
- **按開始不清快取**，只把 `_buff_frozen_at` / `_buff_frozen_view` 清回 `None`。
  清了就要等每個 buff 重新 ADD 才會再出現，而 ADD 一輩子只送一次。
- **沒有任何操作會清空 buff 快取**，「清除」也不會。這與身分綁定的處置一致：
  「清除」清的是統計，buff 是當下的狀態不是統計；而 `ADD` 一輩子只送一次，
  清掉的**無限持續 buff 永遠回不來**（實測踩過：停止 → 清除 → 開始之後就消失了）。
  - 換場景造成的殘留不必擔心：`entityId` 會變，`update_buff_list` 用
    `owner == ident_self_entity` 過濾，舊實體的 buff 自然就不顯示；
    `BUFF_ACTIVE_MAX` 再兜一層上限。
- **buff 名稱查 `effects.ini`**（`load_effect_names()` / `format_buff_name()`），
  查不到才退回 `Buff 0x########`。**不查 `SKILL_NAMES`** —— buffId 與 skill_id
  是不同命名空間，混查只會撞出無關的技能名。
  - **`[Ignore]` 區段**列出不要顯示在面板上的 buffId（假人、測量用的內部效果）。
    只看 key，`0x1234ABCD` 或 `0x1234ABCD = 名稱` 兩種寫法都可以。
    目前 34 筆，全是名稱含「假人」的。
  - **`allow_no_value=True` 是必要的**：`[Ignore]` 可以只寫 buffId 沒有 `= 值`，
    預設會在 `read()` 就丟 `ParsingError`，整份三千多筆一起解不出來。
  - 被忽略的 buff **不進 `active_buffs`**，但診斷 LOG 仍會印並標上 `(已忽略)` ——
    那是開發者模式限定的，留著才查得出「某個 buff 為什麼沒出現在面板上」。
  - 與 `skills.ini` 一樣「每次按開始重讀」，補完 buffId 不必重啟；重讀後會把
    `active_buffs` 裡既有的 `name` 一起重算，否則面板上的舊列會停在 hex，
    直到那個 buff 重新 ADD 才更新。
  - **`configparser` 必須開 `interpolation=None`**：效果名裡有「移動速度+7%」
    這種百分比，預設會把 `%` 當插值語法，而且是 `read()` 之後在 `items()` 才丟
    `InterpolationSyntaxError`，包在 `read()` 的 try 裡攔不到。
  - 打包清單（`MabinogiMobileScribe_BuildTool.sh`、`.github/workflows/build.yaml`）
    已一併加入 `effects.ini`，否則發布版會全部顯示 hex。

## 8. 存檔與圖表的 Buff 持續軸

### 存檔（主程式）

`_snapshot_dict()` 多一個 `buffs` 欄，每列 `[buffId, 名稱, 起, 迄, 層數]`：

```json
"buffs": [["0x53016CBB", "漸強", 1757123456.789, 1757123466.789, 10]]
```

- **時間是 `time.time()` 牆鐘，與 `damage.events` 同一個時鐘**。倒數另外用
  `monotonic`（不受系統時間調整影響），兩套並存，`active_buffs` 同時存
  `end`（monotonic，給倒數）與 `start_wall` / `end_wall`（牆鐘，給存檔）。
- 區間有兩個來源，由 `_buff_intervals()` 合併：
  - 已收到 REM 的 → `buff_history`（REM 當下寫入）
  - 還掛在身上的 → 存檔當下現算：無限持續收在「存檔時刻」，
    有限收在 `min(存檔時刻, end_wall)`。到期沒收到 REM 的因此仍是正確長度。
- **只記 `owner == ident_self_entity` 的**。場上幾十隻怪的 debuff 會把記錄灌爆。
- **區間起點夾到「按下開始」那一刻**（`_monitor_start_wall`，`start_monitoring`
  與 `_reset_stats` 時更新）。開始前就掛在身上的持久型 buff，它的 `start_wall`
  可能是幾十分鐘前，原樣寫進存檔會讓圖表算出超過 100% 的覆蓋率；整段都在開始
  之前的直接跳過。
- **層數一變就切一段**：`start_wall` 是「目前這個層級」的起點。UPD 進來時
  比對 `prev["stacks"]`，變了就把前一段收進 `buff_history` 並從這一刻重新起算；
  沒變就沿用（純粹的重送不切，否則同一個層級會被切成一堆碎塊）。
  一次施放因此可能產生多列，例如 `漸強 ×1` → `漸強 ×10` → `漸強 ×32`。
- `buff_history` 跟 `damage_events` 同進退（`_reset_stats` 一起清）；
  `active_buffs` 不清，理由見 §7。
- **`SAVE_FORMAT_VERSION` 沒有升版**，沿用 `events` 當初的做法：新欄位缺了就當空的，
  舊存檔照樣讀得進來。

### BUFF 統計表（圖表程式，技能統計下方）

欄位 `BUFF名稱 / 覆蓋率 / 生效時間`，依覆蓋秒數由大到小排。

- **區間要夾進 `[0, 場次長度]`**。主程式已經把起點夾到「按下開始」，但**圖表的
  原點是第一筆傷害，不是按開始那一刻**——中間隔了多久就會多出多少，
  不在這裡再夾一次仍會算出超過 100%。夾完長度 ≤0 的整段丟掉（那段不在場次內）。
  兩邊都要夾才保證 ≤100%，只做一邊都不夠。
- **覆蓋秒數要先把區間聯集再算**。同名的不同實體（例如兩個「情緒調節」）可能
  時間重疊，直接把每段長度加總同樣會算出超過 100%。
- 覆蓋率的分母用 **`raw_events` 的實際交手長度**，不是 `base_n_sec`——後者是
  每秒桶的個數（尾端多算一秒），全程掛著的 buff 會算出 99% 這種看起來像有破口的數字。
- 點列 = 加進持續軸（加在尾端），再點一次移除；「清除過濾」全清。
- **點表頭可排序**（名稱／覆蓋率／生效時間），同一欄再點切換升降冪，表頭以 ▲▼ 標示。
  覆蓋率與生效時間是同一個量的兩種寫法，排序鍵共用。
- 版面與技能表對齊靠兩件事：
  - 第 0 欄留白 18px，對上技能表的顏色標記欄，名稱的**起點**才一致。
  - 尾端補一根固定寬度的空欄，讓兩張表的「非伸縮欄總寬」相等。名稱欄是唯一
    `weight=1` 的欄，會把剩餘空間全吃下去；不補的話 BUFF 表只有三欄、拿到的
    剩餘空間遠多於技能表（實測 1400px 視窗下 345px vs 1003px）。補了之後
    1000/1280/1600/1920 四種寬度下兩者完全相等。
- 兩張表用**同一個 grid 容器**、兩列 `weight=1` + `uniform`，高度才是真的對半分。
  用 `pack(expand=True)` 的話會依各自的需求高度分配，技能列多就吃掉大半。

### 圖表（MM Scribe Graph）

- `load_events()` 一併讀 `buffs`；缺這欄就是空 list，圖表照畫，只是下半段是提示文字。
  層數是後加的第 5 欄，只有 4 欄的更早存檔一律當 1 層。
- `_prepare_buff_rows()` 把區間換算成「相對開場的秒數」（原點用 `base_t0`，
  與傷害圖同一個），**依名稱歸成列**——同名的多次施放共用一列。
- **持續軸預設什麼都不畫**，由下方的「BUFF統計」表點選加入。
  `selected_buffs` 用 **list 不是 set**：持續軸的列序就是使用者點擊的順序，
  不重排；表格的名稱前會標上它在持續軸的第幾列。canvas 高度跟著選取數走
  （`_sync_buffbar_height`），沒選時收成一條細線、整片留白——提示字放在
  BUFF 統計的標題列，這裡不重複。
- `_draw_buffs()` 畫在**獨立的 canvas**（`self.buffbar`）而不是塞進傷害圖裡，
  這樣不吃傷害圖的高度。兩個 canvas 用相同的 `padx=8` 與 `PAD_L`/`PAD_R`，
  x 才對得齊。座標換算與傷害圖同一套：

  ```
  slot i 的左緣 = x0 + i * slot_w，slot_w = plot_w / n_slots
  → 時間 t 秒 = x0 + (t - vs) / (n_slots * g) * plot_w
  ```

  （實測誤差 0：第 5 秒的長條 x 與公式算出來的 153.8 完全一致。）
- 縮放／橫移／resize 都走 `_draw_chart()` 末尾的 `_draw_buffs()`，兩張圖同步。
- 名稱畫在**左側欄位、靠右對齊**，位置與傷害圖的縱軸刻度完全相同
  （`x0 - 6`、`anchor="e"`），兩張圖的左緣才連成一條線。
  欄寬就是 `PAD_L`(62) 扣掉那 6px = **56px**，8pt 大約只裝得下 4 個中文字，
  超出的用 `_fit_buff_name()` 量實際字寬後截斷加省略號
  （不截會直接畫出 canvas 左緣，看起來像壞掉）。要放更長的名字就調 `PAD_L`
  ——它同時是傷害圖的左內距，兩邊會一起變寬，對齊不會跑掉。
- **被截斷的名稱可以 hover 看全名**（`_on_buff_motion`）：
  - 只記被截斷的那幾列（`_buff_name_hits`）。滑過完整的名字還跳一個一模一樣的
    tooltip 只是干擾。
  - 命中範圍取**整列高**，不是只有文字那幾 px——8pt 的字高不到 11px，
    逼使用者精準壓在字上等於這功能不能用。
  - 只在 `x < x0`（名稱欄）內作用，長條區不理。
  - tooltip 畫在 buffbar canvas 上，貼到右緣／下緣會自動翻邊——這個 canvas
    只有幾十 px 高，不翻的話會有一半在外面看不到。
- 每個方塊右緣讓出 `BUFF_SEG_GAP`(2px)。層數一變就切一段，相鄰兩段的時間是連續的，
  不留空隙會黏成一條、看不出切在哪。
- 層數標在方塊開頭（`×N`）。**1 層不標**，與主程式面板同一個規則；方塊窄於
  `BUFF_STACK_MIN_W`(18px) 也不標（字會溢出到隔壁）；被視野左緣裁掉的那段也不標
  ——標在裁切點上會讓人以為那裡就是起點。
- **hover 傷害長條時，同時段生效的 buff 方塊會提亮**（`_highlight_buffs`）：
  - 長條平常畫 `COL_BUFF_BAR`(暗綠)，命中時換 `COL_BUFF_BAR_HI`(亮綠)，
    `_clear_hover` 一併還原。
  - 判定是「方塊與這一格的時間範圍有交集」（`st < hi and en > lo`）——
    併格時一格代表好幾秒，用交集而不是包含。
  - 只作用在持續軸上真的畫出來的方塊：沒被選進時間軸的 buff 本來就沒有 canvas
    item，自然不會被提亮，不必另外過濾。
  - 層數文字改用淺色 `COL_BUFF_STACK_TXT`——原本的深色字在暗綠底上會糊掉。
- 尺寸與配色都在檔頭常數：`BUFF_ROW_H` / `BUFF_BAR_H` / `BUFF_NAME_PT` /
  `BUFF_STACK_PT` / `COL_BUFF_BAR` / `COL_BUFF_BAR_HI` / `COL_BUFF_NAME` /
  `COL_BUFF_STACK_TXT`。
