# MM Scribe — 角色身分偵測技術筆記

> 怎麼從封包認出「哪個實體 ID 是我自己」。
>
> **最後更新：2026-08-16** — 規則來自 `Note/Ref/for-mm-scribe-identity.md`（協作者台版實測），
> 本地照著實作並**已驗證通過**：換兩張地圖，`★ 自己` 綁定的實體 ID 與該圖 `[Flag]` 行的攻擊者 ID 相同。
>
> **傷害統計已改為依賴這套偵測**：沒有角色 ID 就完全不記錄，有了也只記「攻擊者 == 自己」的傷害。
> 狀態以紅字／綠字寫在攻擊事件日誌上（見 §6）。

---

## 1. 先分清楚兩種 ID

| | 是什麼 | 會不會變 |
|---|---|---|
| **實體 ID**（entityId, UInt32） | 這次連線的「演員編號」。傷害封包的攻擊者／目標欄位就是它 | **換場景就換** |
| **角色身分**（帳號碼 + 角色索引） | 這個角色到底是誰，跟連線無關 | **不變** |

認出「自己」不是靠某個旗標，是把兩者對上：**先知道自己的身分，再反查哪個實體 ID 的身分跟自己一樣**。

> 走過的死路（協作者已驗證，別再試）：找「恆等於自己」的欄位（掃遍 opcode × 位移 0～64，0 個）、
> 血量 blob 加密差異（沒差異）、「自己是唯一橫跨所有場景的實體」（0 個實體符合，連自己都不是）。

## 2. 要用的兩則訊息（台版 2026-08-16 實測值）

`packetType` 來自伺服器下發的遠端目錄，**會隨區服／改版變動**，跟 `0x51E9`／`0x4FC5` 一樣不是協定常數。

### A. 我的角色資料 `0x00004FFF`

遊戲**只發給本人**，所以它本身就是自己的身分。

| 項目 | 實測 |
|---|---|
| 標頭 | 9-byte：`[u32 packetType][i32 contentLength][u8 encodingType]`，`enc=1`（Brotli） |
| 框 | **unframed**（沒有 FrameStart/FrameEnd，直接就是標頭 + body） |
| 大小 | 壓縮後 **116,397 / 116,434 / 116,545 bytes**（每次換場景都不同） |
| 送出時機 | **每次換場景送一次**（本地三次換圖各一則） |

解壓後前 8 bytes 就是身分，**跟區服／版本無關**：

```
off  size  欄位
 0    2    characterIndex  (u16 LE)
 2    4    accountInfo     (u32 LE)   ← 帳號碼
 6    2    reserved                    ← 必須是 0（拿來擋假陽性）
```

實測餵入約 **1.3KB** 壓縮位元組（第一個 TCP 分段）串流解壓器就吐得出這 8 bytes，
所以**不必收完 116KB**（也不可能可靠收完，見 §5）。

### B. 玩家出現 `0x00004E4F`

每個玩家進入視野時送，同時帶著實體 ID 與該玩家的身分。

| 項目 | 實測 |
|---|---|
| 框 | framed，`enc=1` |
| 大小 | 壓縮後約 **1.3KB**（1296B），解壓後約 **3.5KB** |
| 解壓後 +0 | `u32 entityId` |
| `characterId` | `u64`，位在解壓後 **約 +2600**（實測 +2604 / +2605；**位移不是常數，一律用搜尋，不要寫死**） |

```
characterId = accountInfo << 16 | characterIndex
```

> 16 位這個拆法是靠 A 訊息的 `accountInfo` 釘死的——兩條完全獨立的訊息對上同一個數字。
> 只看 B 訊息會分不出 16 位還是 20 位（角色索引很小的話兩種拆法算出的索引一樣）。

## 3. 演算法

1. 收到 **A** → 取出我的身分 `(帳號碼, 角色索引)` 存起來
2. 收到 **B** → 解壓，讀 `entityId`，在內容裡搜 `u64 characterId`
3. **比對**：`characterId == 我的帳號碼 << 16 | 我的角色索引` → 那個 `entityId` 就是「我」
4. 之後 `isSelf(id) = (id == selfEntityId)`

**兩個方向都要做**，誰先到都行：A 先到就回頭掃已快取的 B；B 先到就在每次有人出現時順手比對。

### 比對鍵一定要兩個都相等

- 只比帳號碼 → 綁到同帳號的別隻角色
- 只比角色索引 → 撞到別的帳號（索引 4、5 這種小數字滿地都是）

### 換場景 / 換角色

| 事件 | 訊號 | 動作 |
|---|---|---|
| 換場景 | 收到 A，身分**不變** | **一定解除實體綁定**，身分留著重新比對新場景的玩家 |
| 換角色 | 收到 A，身分**改變** | 清掉身分與綁定，重新偵測 |

> 這裡踩過坑：初版看到「身分相同」就維持綁定，結果沿用上一張圖的實體 ID，
> 傷害日誌把別人標成自己。**A 訊息 = 場景換了 = 實體 ID 一定變**，沒有例外。

**不要存角色名當身分**——名字換角色就過期，而過期的名字會把「我」綁到場上另一個人身上。

## 4. 程式實作對照（`Source/MabinogiMobileScribe_Beta.py`）

| 函式 | 做什麼 |
|---|---|
| `_scan_identity` / `_ident_walk` | 入口。依 TCP 連線 key 走訊息狀態機 |
| `_ident_open` / `_ident_feed` | 開一則訊息、把跨封包的 body 接續餵進串流解壓器 |
| `_ident_apply_self` | A 訊息 → 身分；**一律解除舊綁定**、重置本場統計 |
| `_ident_finish_appear` | B 訊息收尾 → 實體 ID + 比對 |
| `_ident_match_offset` / `_ident_bind` | 搜 `characterId`、綁定並記 LOG |
| `_ident_rescan_cache` | A 晚到時回頭掃快取的 B |

幾個關鍵設計，改動前先看懂：

- **訊息狀態機，不是逐封包解析**。`characterId` 在解壓後 2600 bytes 之後，而 B 訊息的 body 會跨 2～3 個 TCP 分段；只解單一分段內那一截永遠讀不到（初版就是這樣，換場景後 0 命中）。
- **依連線分流**（`(src, sport, dst, dport)`，上限 `IDENT_STREAM_MAX`）。混到別條連線的位元組會把串流解壓弄壞。
- **A 訊息吐出前 8 bytes 後轉 skip 模式**：剩下 116KB 只倒數不解壓。不轉 skip 的話，後續幾十個封包的壓縮位元組會被當成訊息邊界亂掃。
- **偵測不受「開始 / 停止」與開發者模式影響**：攔截執行緒程式一啟動就跑（`_ensure_sniffer`）。換場景那一瞬間的 A/B 只送一次，沒在收就要等下次換圖。
- `reserved != 0` 是 A 訊息唯一的假陽性擋牆（unframed 只能逐 byte 找 magic）。

## 5. 已知限制

- **本工具不做 TCP 重組**。狀態機假設封包依序、連續；**重傳或亂序會直接打斷串流解壓**，該則訊息就丟掉（LOG 會記一行）。實測可用，但這是最脆弱的一環——若某次換場景一直綁不上，第一個懷疑這裡。
- `characterId` 的位移不是常數，靠搜尋；理論上可能撞到別的欄位剛好等於同一個 u64（實測未發生，且 8 bytes 全等的機率極低）。
- 需要 `brotli`。**這是硬相依，不是選用的**：0x4FFF / 0x4E4F 都是 `enc=1`（Brotli），
  沒裝就完全無法偵測 —— 而 §9 的門檻會讓傷害統計連帶整個空白。
  三份安裝清單（`README.md`、`run-macos.sh`、`.github/workflows/build-macos.yml`）
  都必須列上 `Brotli==1.1.0`；曾經漏過一次，症狀是紅字「尚未偵測到角色ID」，
  而那句話會把人導去換地圖，換幾次都不會好。缺套件時改報 `IDENT_MSG_NO_BROTLI`。

## 6. 攻擊事件日誌上的狀態列

| 狀態 | 日誌 | 顏色 | 寫出時機 |
|---|---|---|---|
| 未取得 | `尚未偵測到角色ID，請嘗試更換地圖或重新登入來獲取角色ID` | 紅 | 程式啟動／按「開始」／按「清除」時仍未綁定，或**真的有傷害因此被丟掉**（每場一次） |
| 已取得 | `已獲得角色ID資訊` | 綠 | **整個 session 只在首次取得時寫一次** |

刻意的取捨：

- 綠字不隨換場景重新綁定、也不隨按「開始」重報 —— 那是正常狀態，重報只是洗版。
- 換場景解除綁定的當下**不寫紅字**：綁定通常一秒內就補回來，提早報會變成每次換圖閃一行紅字。
  真的有傷害進不了統計時才出聲（`parse_payload` 的門檻處呼叫 `_ident_warn_no_id`）。

**「清除」不會清掉身分與綁定**(同 `local_player_id` 的處置)——清了就得等下次換地圖才會再認出自己,
中間所有傷害都不會被記錄。

實作：`_ident_notify_ok` / `_ident_warn_no_id` / `_ident_status_line`，
顏色走 `log_area` 的 `highlight`（紅）與 `ident_ok`（綠）tag。

## 7. 開發者 LOG 怎麼看

```
[ID] 我的角色資料 type=0x4FFF len=116434 enc=1 (第1次)
[ID] 我的身分: 帳號碼=XXXXXX 角色索引=N | characterId=0x... (收 1323B 後解出)
[ID] ★ 自己 = 實體 0x00B4C045 (本場首次綁定) | characterId 位於解壓後位移 +2605
[ID] 場景更新 (身分不變: ...),解除舊綁定 0x00B4C045,等待重新比對
[ID] ⚠ 本場尚未綁定 — 已收到 18 筆出現訊息 (完整 12 筆, 命中 0 筆)
[Flag] 數值: 8309 | 攻擊者:0x00B5FF8F → 目標:0x00B6044E ←自己 | ...
```

- 別人的出現訊息**不寫 LOG**（一次換圖十幾筆會洗版），只累計數字給「⚠ 本場尚未綁定」那行用。
- 那行的 `完整 M 筆` 是分辨故障原因的關鍵：
  - 收到很多筆、完整也多、命中 0 → 換場景時遊戲**沒送自己的登場訊息**，得另闢管道
  - 完整筆數遠少於收到筆數 → **重組不夠**（重傳／亂序打斷）

## 8. 與其他自身 ID 來源的關係

治癒端另有一套獨立的本地 ID 學習（`0x502A` 旗標，見 `MM_Scribe_PacketNotes_Heal.md` §5）。
兩者互為佐證：綁定成功時若 `local_player_id` 已學到，LOG 會多印一行比對結果。

該筆記 §5 提到的限制「治療前無法識別自身」，正是這套身分偵測要解掉的問題——
身分偵測**不需要戰鬥、不需要被治療**，換場景時就能認出自己。

## 9. 統計門檻（傷害端）

`parse_payload` 讀出 `attacker_id`（`content+0` = `offset+9`）後：

```
is_self_hit = (ident_self_entity is not None) and (attacker_id == ident_self_entity)
```

`is_self_hit` 為假就整筆跳過——不進 DPS／覆蓋率／技能排行／日誌，傷害免疫那筆也一樣。
**開發者面板不受這道門檻影響**（別人的傷害照印），那是驗證身分偵測對不對的唯一依據。

副作用要記著：

- 寵物、隊友、敵人打的傷害全部不再入帳。寵物若是獨立實體，`忽略寵物攻擊` 這個設定實質上已被身分門檻取代。
- **DoT／地面傷害的 `attacker_id` 是否等於施法者本人，本地尚未驗證**。若某些技能的持續傷害掛在別的實體上，那些跳數會整批消失——統計明顯偏低時第一個查這裡。
